# وثيقة تصميم قاعدة البيانات (Database Schema Documentation)
## نظام إدارة ورشة ميكانيكا السيارات

---

## 1. المبادئ التصميمية (Design Principles)

1. **العلاقات التكاملية الصارمة (Strict Referential Integrity):** مفاتيح أجنبية لجميع الجداول مع `ON DELETE RESTRICT` للسجلات الحساسة (الفواتير، حركات المخزون، أوامر العمل) و `ON DELETE CASCADE` للجداول التابعة الثانوية (عناصر الفاتورة، أكواد التقرير).
2. **الحذف اللطيف (Soft Delete):** استخدام حقل `deleted_at TIMESTAMP NULL` للعملاء، السيارات، المستخدمين، وقطع الغيار لمنع ضياع السجلات وتاريخ المعاملات.
3. **التدقيق والأثر (Audit Trail):** تسجيل `created_by`, `updated_by`, `created_at`, `updated_at` في كافة الجداول التشغيلية.
4. **العزل والأمان (Multi-Tenant Ready):** حقل `workshop_id` في الجداول لتسهيل دعم الفروع أو الورش المتعددة دون إعادة هيكلة.
5. **منع التكرار (Idempotency):** دعم `idempotency_key` في حركات المخزون والمدفوعات لمنع الخصم المزدوج.

## 3. العلاقات التكاملية الهامة (Key Schema Constraints)

1. **السيارات والعملاء:** 
   - `vehicles.current_owner_id` يشير إلى `customers.id`.
   - يتم تسجيل أي تغيير للمالك في `vehicle_ownership_history` تلقائياً لحفظ التاريخ للمالك السابق دون تشويه فواتيره.
2. **الزيارات وأوامر العمل:**
   - الزيارة `visits` تمثل دخولاً فعلياً للورشة وتحتوي على أمر عمل `work_orders` أو أكثر.
   - لا يمكن حذف زيارة تحتوي على أمر عمل مكتمل أو فاتورة صادرة.
3. **خصم المخزون والعمليات المكررة:**
   - جدول `stock_movements` يمتلك قيد `UNIQUE(idempotency_key)`، بحيث إذا أعاد جهاز الموبايل إرسال طلب صرف القطعة نتيجة ضعف شبكة، يُرفض الطلب المكرر ويُعاد تأكيد العملية السابقة دون خصم جديد.
4. **الفواتير والمدفوعات:**
   - `invoices.paid_amount` يُحسب برمجياً أو عبر Triggers كمجموع `payments.amount`.
   - حالة الفاتورة تتغير تلقائياً: `unpaid` -> `partially_paid` -> `paid`.
